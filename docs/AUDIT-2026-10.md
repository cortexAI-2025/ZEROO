## 3. Choix de conception retenus

- **Formules** : une formule est un produit dont les composants sont des groupes d'options obligatoires (système existant). Pas de nouveau modèle de prix.
- **Créneaux** : table dédiée évaluée dans le fuseau de l'établissement, avec passage de minuit, comme les horaires d'ouverture.
- **Modes de commande** : `offers_pickup` (nouveau) + `delivery_enabled` (existant, réservé à Pro). Une dark kitchen n'a pas de retrait par défaut.
- **Règles métier côté serveur** : toute vérification (mode, créneau, prix promotionnel, quota, disponibilité livreur) est refaite dans `create_order`, jamais seulement dans l'app.
- **Aucun changement de modèle économique** : pas de frais de service, pas de commission, pas de Stripe Connect.

## 4. Environnement de test

`scripts/localdb/run.sh` recrée une base Postgres locale (PostGIS, pgTAP, pg_cron), simule les parties propres à Supabase (`auth`, rôles, `vault`, `storage`, `pg_net`), rejoue les migrations, charge `supabase/seed.sql`, puis exécute les tests pgTAP. Il remplace `supabase test db` quand Docker n'est pas disponible. Prérequis : paquets `postgresql-16-postgis-3`, `postgresql-16-pgtap`, `postgresql-16-cron`.

```
PGUSER=postgres PGHOST=localhost scripts/localdb/run.sh
```

Limite : ce n'est pas une instance Supabase (pas de GoTrue, de PostgREST ni d'Edge Runtime). Les tests de bout en bout (`npm run e2e`) restent à exécuter avec `supabase start`.
