# Contrôle sécurité et cohérence — 28 octobre 2026

Périmètre : site public zeeroo.fr (GitHub Pages), application app.zeeroo.fr,
console zeeroo-admin.vercel.app, API Supabase de production. Contrôle ciblé du
code, des accès serveur, des déploiements et de parcours web. Ce document ne
constitue pas un audit exhaustif ni une certification.

## Constats et corrections

- Les accès anonymes testés aux profils, commandes, abonnements, livreurs,
  rôles, dossiers et communications privées sont refusés par l’API. Toutes
  les tables publiques ordinaires inspectées ont RLS activée.
- Les droits anonymes inutiles sur admin_profiles ont été retirés. Les
  politiques limitent chaque profil administrateur à son propriétaire qui
  doit aussi être administrateur. Cette table et la lecture de sa propre
  appartenance avaient été provisionnées hors migrations : des migrations
  de référence rendent leur reconstruction reproductible.
- Le dashboard efface les données affichées à la déconnexion et invalide
  les réponses tardives. Les vérifications de session concurrentes ne
  peuvent pas réouvrir un ancien compte. Le serveur conserve son contrôle
  d’autorisation indépendant de l’interface.
- Les dossiers clients et abonnés relisent prénom, nom, adresse, téléphone
  et e-mail courant via une projection administrateur explicite. Aucun
  mot de passe, jeton Auth ou donnée bancaire n’est retourné.
- Les revendications de l’annuaire public disposent maintenant d’une file
  de traitement dans le dashboard : décision motivée ; acceptation liée
  à un restaurant dont le propriétaire et le SIRET correspondent. Aucun
  abonnement, mini-site ni publication n’est créé automatiquement.
- Le compte administrateur de l’application propose le dashboard complet
  distinctement de la gestion interne des campagnes.
- Les configurations Vercel ajoutent nosniff, refus d’intégration en iframe,
  politique de référent et restriction des objets/base HTML. La CSP reste
  partielle : elle ne contraint pas encore toutes les sources de scripts.
- Le webhook Stripe déployé était antérieur au correctif déjà versionné :
  relecture de l’abonnement actuel et protection contre les événements
  tardifs d’un ancien abonnement. Le déploiement doit reprendre exactement
  les fichiers testés, sans changer SDK, version API ni secrets.
- La branche de correction réunit l’application et les fichiers du dashboard
  en préservant les derniers profils client, au lieu de deux versions divergentes.

## Vérifications

- npm run check : TypeScript, lint, formatage, 232 tests Jest réussis.
- Dashboard : 24 tests Node réussis (accès, données, modération,
  échappement HTML, revendications, réponses tardives, déconnexion).
- Site public : 11 tests réussis ; annuaire affiché avec 25 lignes par page,
  2 390 références réelles ; démo isolée sans appel Supabase ni Stripe.
- Parcours navigateur publics sur mobile et ordinateur : pas de données
  privées sans connexion ; pas de débordement horizontal sur les vues testées.
- Scénarios de droits et d’identité exercés en transaction annulée sur la
  base réelle, sans compte ni revendication de test conservés.
- La commande locale db:test ne peut pas joindre PostgreSQL local ; la CI
  rejoue les migrations et les tests pgTAP sur une base jetable. Les tests
  Deno locaux sont bloqués par l’accès aux registres ; leur résultat de CI
  doit être contrôlé avant déploiement du webhook.
- Aucun paiement réel, e-mail, SMS ni notification réelle envoyé. Les tests
  ne couvrent pas un binaire iOS/Android ou toutes les opérations de production.

## Points restant à traiter

1. admin.zeeroo.fr renvoie encore à l’ancien prototype. DNS externe IONOS :
   remplacer seulement l’enregistrement admin (actuellement A 185.158.133.1)
   par le CNAME 441819a6ee9b4995.vercel-dns-017.com recommandé par Vercel.
   Contrôler à nouveau DNS et certificat après propagation. En attendant,
   utiliser https://zeeroo-admin.vercel.app. Aucun changement des NS, de la
   racine ou du sous-domaine app n’est nécessaire.
2. La protection Supabase contre les mots de passe compromis est désactivée.
   Son activation dépend de l’offre et du réglage Auth dans Supabase ; aucun
   changement d’offre ni de mot de passe n’a été effectué. L’absence de MFA
   reste le choix explicite du propriétaire.
3. GitHub Pages ne fournit pas les en-têtes HTTP de durcissement configurés
   sur Vercel. Leur ajout exige une évolution d’hébergement ou un proxy.
4. ~~Le SDK Supabase du dashboard est chargé depuis un CDN versionné.~~ **Traité** :
   le client (2.117.3) est embarqué dans `admin-web/vendor/supabase.js` (empreinte
   SHA-256 vérifiée par `admin-web/security.test.cjs`) et la CSP de
   `admin-web/vercel.json` n'autorise plus que `script-src 'self'` et les connexions
   vers le projet Supabase. Aucun script tiers n'est exécuté par la console.
5. ~~Historique de migrations différent de la production.~~ **Traité** : les fichiers
   `…104925`, `…105756`, `…111700`, `…112112` portent désormais les versions réellement
   appliquées, et `…090600` / `…091208` (appliquées en production sans fichier Git) sont
   versionnées à l'identique depuis `supabase_migrations.schema_migrations`. Les versions
   Git et production sont alignées ; aucun `supabase migration repair` n'est nécessaire.
   Restent à appliquer en production : `20261025130000_affiliated_directory` et
   `20261025140000_publication_guard`.

Les alertes de fonctions SECURITY DEFINER ne constituent pas à elles seules
une faille : les fonctions privées contrôlées vérifient identité et rôle. Les
tables RLS sans politique restent fermées par défaut. Les journaux ne prouvent
pas l’absence de tout incident ; le contrôle reste limité à la période inspectée.
